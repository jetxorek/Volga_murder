# ADR-005. Граница SaveState ↔ UI-состояние

**Дата:** 2026-01-20
**Статус:** Принято

## Контекст

Стор содержит и save-поля (влияют на дальнейшую игру), и UI-поля (актуальны только в текущей сессии: какой экран открыт, показан ли toast). Если UI-поле попадёт в `SaveState`, оно восстановится при загрузке — но это бессмысленно (toast от вчерашней сессии). Если save-поле не попадёт в `SaveState`, прогресс теряется при перезагрузке.

## Решение

1. `SaveState` — **ровно 18 полей** по схеме `SaveStateSchema` (`.strict()` в P1b гарантирует, что лишнее поле не пройдёт).
2. UI-поля живут в отдельном слайсе `ui`, **никогда** не попадают в `toSaveState`.
3. Граница реализуется двумя функциями:
   - `toSaveState(store): SaveState` — вызывается в `persist.partialize`. Возвращает только save-поля. Лишнее поле — баг (упадёт на валидации Zod при загрузке).
   - `fromSaveState(save): Partial<Store>` — вызывается при загрузке. Возвращает только save-поля. UI-поля **не затираются** — остаются со значениями по умолчанию.
4. `pendingNextScene` — UI-поле (следующая сцена после сводки главы). Если игрок перезагрузится на экране сводки — поле теряется. **Решение:** при загрузке восстанавливать из `end`-узла текущей сцены (чтение `data`, не хранение UI-поля в сейве). Это реализуется в `loadGame` (P4b).

## Последствия

- Любое новое поле стора требует явного решения: save или UI.
- Тест `toSaveState` падает, если в `SaveState` попало UI-поле (Zod `.strict()`).
- Тест `fromSaveState` проверяет, что UI-поля не затираются.
- Список save-полей — в `saveStateMapper.ts`, комментирован.
